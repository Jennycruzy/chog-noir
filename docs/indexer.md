# Live transfer indexer

Run `pnpm indexer:live runs/live-indexer <inclusive-start-block>` with the existing local `HYPERSYNC_TOKEN`. Use the same directory and start block to resume. `MONAD_RPC_WS` optionally overrides the public subscription endpoint. `INDEXER_RUN_SECONDS=25` limits a smoke check; otherwise the process runs until SIGINT or SIGTERM.

Run `pnpm indexer:reliability` to launch a detached six-hour check in a new timestamped directory under `runs/reliability/`. It uses the history service's current exclusive height as its inclusive starting point. `launch.json` records its process ID; `monitor.log` records subscription and catch-up activity. `run-summary.json` records progress and the planned end time. Keep the host awake and connected for the observation window. The launcher returning successfully means the child was spawned; confirm the summary and log before treating it as running.

At timed shutdown the monitor catches up once more and fetches a fresh full-range history reference, saved as `reference-page-*.json`. `reliability-report.json` compares every transfer identity and its decoded content against incremental ingestion. A timed completed run with exact coverage, no duplicates, no unresolved review findings and at least one transfer can pass. A signal-stopped run is `INTERRUPTED`; zero activity is `INCONCLUSIVE`; comparison errors or mismatches are `ERROR` or `FAIL`. The reference is a separate query to the same HyperSync service, not a second provider. This report evaluates ingestion completeness. Restarting a completed or interrupted monitor with a new duration starts a new observation period and does not stitch elapsed time into a six-hour pass.

The monitor subscribes to Chog transfers and attempts history catch-up on startup, subscription acknowledgement, connection close and every ten seconds. Polling continues while the socket is disconnected. Subscription rejection, acknowledgement timeout and missed heartbeats trigger reconnects. A history failure preserves the checkpoint and is retried on the next trigger. Recovery requests are serialized; the CLI coalesces overlapping triggers.

WebSocket observations are saved atomically in `observations.json`. They are provisional and never advance the contiguous history checkpoint. Complete history source pages and the checkpoint are stored under `recovery/`. History corroborated transfers appear once, ordered by block and log index, in `snapshot.json`. Live observations beyond history coverage appear under `pending`; they are not added to the snapshot's `logs`. The `recovered` list means history transfers absent from this directory's saved live observations, including older transfers fetched at startup; it is not a count of failures during the current process.

Consumers must check `status`, `checkedAt` and `toBlockExclusive` before using a snapshot. `PASS` means the saved observations agree with the covered history, not that the monitor is still connected, caught up to the current chain head, or that those blocks are final. Failed sync attempts leave the previous snapshot and its coverage timestamp intact. An empty new run has no usable snapshot until its first successful catch-up.

Unmatched live events inside the covered range, changed transfer content and removed logs require `REVIEW`. Receiving a removal immediately invalidates the snapshot even if history subsequently becomes unavailable. Removal evidence survives restarts and re-additions. Reorg rollback is not implemented: investigate and rebuild in a separate directory rather than using a reviewed snapshot for cases. The monitor does not write into PostgreSQL or publish game events.

One writer owns `.monitor-lock`; recovery also uses `recovery/.lock`. Normal exit and caught errors release these locks. A forcibly killed process may leave a lock directory. Confirm that its writer has stopped before removing an empty stale lock and restarting. Missing committed source pages, incompatible start blocks and conflicting source records fail closed.

Tests use the real six-hour source fixture with injected history responses. They cover duplicate live messages, catch-up over disconnect gaps, process restart, provider failure and retry, delayed history, removal persistence, conflicting observations and concurrent sync requests. The network smoke check confirms subscription acknowledgement and periodic catch-up; it does not replace a complete six-hour observation or prove recovery across a real forced network outage.
